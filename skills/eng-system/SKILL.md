# eng-system · 总入口

先回答一个问题：**你现在处在哪个阶段？** 再决定用哪个技能。

> 本技能不产出文档，只做路由。真正的动作在其余 6 个技能里。

---

## 一、阶段判断

| 你的处境 | 用哪个技能 |
|---|---|
| 刚接手一个陌生项目，想知道从哪读 | §二 接手导览 |
| 要从零起一个项目 | `eng-bootstrap`（先看 §三 选路径） |
| 项目已有一堆文档，想补建规范 | `eng-bootstrap` 的「补建/迁移」 |
| 有了调研，要把结论固化成规格 | `eng-architecture` |
| 要把范围切成可交付的几段 | `eng-milestone` |
| 要核实某个外部能力 | `eng-research` |
| 要做取舍 / 推翻旧决定 | `eng-decision` |
| 文档多了要校对 / 准备冻结 | `eng-audit` |
| 已开工，想知道每轮怎么收尾 | §五 执行闭环 |
| 要交接给下一个会话 | §七 交接清单 |

## 二、接手导览（读什么、按什么顺序）

```
1. AGENTS.md      → 不可违反的规约（先读这个，避免一上手就违规）
2. ROADMAP.md     → 现在在哪个里程碑、什么版本、哪些决策已定
3. 当前里程碑文档 → 目标 / 非目标 / 前置调研 / 交付物 / 门禁
4. 相关架构文档   → 只读与你任务相关的章节，不要通读
5. 相关调研       → 只在「为什么这么定」有疑问时读
```

三条判读技巧：

| 想知道的 | 去哪找 |
|---|---|
| 什么**不能**做 | `AGENTS.md` 的「明确不做的事」 |
| 什么**已经定了** | `ROADMAP.md` 的决策索引 |
| 什么**还没定** | 里程碑的「风险与未决」+ 调研的「待确认」 |

**如果这五样里缺了某一个**，说明项目还没 bootstrap 完整——转到 `eng-bootstrap` 的「补建/迁移」，不要凭空开工。

## 三、两条合法路径（不是一条）

`README` 里那种「bootstrap → milestone → research」的单线顺序**只适用于一种情况**。真实有两种：

### 路径 A：骨架先行（先立规矩，边做边想）

适用：范围清楚、技术栈确定、需求不会再大改。

```
eng-bootstrap → eng-milestone →（每个里程碑前）eng-research → eng-audit
```

风险：能力边界靠猜。若猜错，返工落在 ROADMAP/AGENTS 的全部下游。

### 路径 B：调研先行（不想清楚不动手）

适用：**范围本身不确定**、技术可行性未知、需要比较多个方案。

```
（最小目录）→ eng-research ×N → eng-decision → eng-architecture → eng-bootstrap（定稿）→ eng-milestone
```

关键差别：**先只建 `docs/research/` 与 `_refs/`，跑完调研再冻结骨架。** 不要在能力边界还没搞清时就把 AGENTS 写死。

**判断标准**：如果你现在答不上「这个项目明确不做什么」和「技术栈约束是什么」，就走路径 B。

## 四、轻量分档（不要对小事用重流程）

| 项目规模 | 必做 | 可跳过 |
|---|---|---|
| **一次性脚本 / 单文件** | `eng-decision` 记一行；调研结论带标注 | 骨架、里程碑、audit、覆盖率 |
| **小工具（≤3 里程碑）** | 骨架（简化版）+ 里程碑九段（数据模型 / 故障注入可标 N/A）+ 覆盖率门禁 | audit 冻结、架构规格（若只有单一模块） |
| **完整体系（≥4 里程碑 / 多人 / 长期维护）** | 全部 7 个技能 | — |

三条「可以不做」的明示：

- **每个技能都可以单独触发。** 只用 `eng-research` 也成立——产物就是一份带四档标注的 md，不需要建四个 docs 子目录。
- **覆盖率门禁只在进入编码阶段后生效**，文档阶段一律标 `N/A`，不要写「待达标」。
- **架构规格在单一模块的小项目里可以省略**——但一旦出现「跨模块约束」，就必须单独成文。

## 五、执行闭环（开工之后每轮做什么）

技能组最容易漏掉的就是这一半：**开工前写得很好，开工后没人管**。

每完成一个可交付单元，按顺序做五件事：

```
1. 测试     跑该单元对应的测试；不达标不提交
2. 文档     若行为变化 → 更新对应架构章节（追加「校准」节，不重写）
3. CHANGELOG 只记用户可感知的变化；重构/注释/测试不记
4. 版本     z 位 +1（同一里程碑内）；跨里程碑才动 y
5. ROADMAP  更新该里程碑状态行（⏳ → 🔄 → ✅）
```

### 里程碑验收动作（原来没有归属）

里程碑做完时，**由发起人**（通常是执行者）主动发起验收，不是等别人来问：

```
1. 逐条打勾验收门禁，不达标项写明原因与补偿措施
2. 填写「验收记录」：实际覆盖率、未达标项、遗留技术债
3. 打 x.y.0 tag
4. ROADMAP 状态改 ✅，CHANGELOG 从 Unreleased 切到 [x.y.0]
5. 若本里程碑推翻了任何既有结论 → 走 `eng-research` 的「推翻与回写」清单
```

## 六、发版（原来没有归属）

```
1. 从 CHANGELOG 的 [Unreleased] 里切出本次范围
2. 建 [x.y.z] - YYYY-MM-DD 段落
3. 破坏性变更单列 ### 破坏性变更 并写迁移方式
4. git tag vx.y.z
5. 确认 ROADMAP 的版本区间与本版本一致
```

**判据**：版本号必须能在 ROADMAP 里找到归属的里程碑。找不到，说明不是「版本」而是「随手改」。

## 七、交接清单（会话结束 / 换人时）

写完这五条，下一个会话才能无缝接上：

```
[ ] 当前里程碑状态行已更新（做到哪一步、下一步是什么）
[ ] 本轮新产生的结论已挂到对应索引（调研索引 / 决策索引 / 架构章节）
[ ] 本轮推翻的旧结论，已按「推翻与回写」清单改完所有受影响文件
[ ] 未完成的工作写清了「卡在哪、需要谁做什么」
[ ] 下一轮的第一件事（一句话）
```

**不要用「进度正常」这类话交接。** 接手者要的是「下一步做什么」和「哪里有坑」。

---

## 八、交付汇报格式（每个技能都该用）

技能执行完，回给用户的话必须包含三部分，缺一不可：

```
1. 做了什么   —— 产出了哪些文件（给路径）
2. 没做什么   —— 做了但没通过的、跳过的、以及为什么
3. 下一步     —— 建议用哪个技能 / 需要用户拍板什么
```

**只报「已完成」而不报「没做到什么」，等于隐藏风险。**

---

## 九、反模式

| 反模式 | 后果 |
|---|---|
| 跳过阶段判断，直接动手 | 在错的阶段用错的技能，产物要重做 |
| 对 200 行脚本用全套流程 | 仪式成本高于收益，最后没人真执行 |
| 交接只写「进度正常」 | 接手者不知道下一步做什么、哪里有坑 |
| 只报「已完成」不报「没做到」 | 隐藏风险，下次在同一个坑里再摔 |
| 能力和约束没想清就写 AGENTS | 骨架返工，连累全部下游 |
| 把技能当流程流水线强制执行 | 技能可单独用；强拼成一条线会卡在不适用的环节 |

## 十、自检

```
[ ] 已判断当前阶段，并选定了对应技能
[ ] 若范围不确定，走的是「调研先行」而不是硬写骨架
[ ] 按规模选了对等的档位，没对小事用重流程
[ ] 交付汇报含「做了什么 / 没做什么 / 下一步」三段
[ ] 若在交接：五条清单已写完，且写了下一轮第一件事
```

## 十一、技能地图

```
eng-system（本技能：路由 + 接手 + 轻量 + 执行 + 发版 + 交接）
   ├─ eng-bootstrap     建骨架（三种入口：冷启动 / 调研先行 / 补建迁移）
   ├─ eng-research      取证（四档标注 / 推翻与回写）
   │     └─ eng-decision    取舍（六段 / superseded）
   │           └─ eng-architecture  固化规格（约束表 / 校准节）
   │                 └─ eng-milestone   切范围（九段 / 阶段分档门禁）
   └─ eng-audit         校对（审查 / 修复 两个阶段）+ 冻结
```

> 箭头不代表必须串行——它表示「产物被下游引用」的方向。
