# eng-audit · 一致性与逻辑审查

文档超过 10 份后，人会记住「最新结论」，但记不住「旧结论还残留在哪」。残留的旧结论会以「引用错编号」「按废弃方案设计」的方式变成真实 bug。

> 模板：`../../templates/review.md.tpl`。产物路径见 §七。

---

## 一、两个阶段，不要混（本技能最容易做错的地方）

| 阶段 | 做什么 | 允许改文件吗 |
|---|---|---|
| **阶段一 · 审查** | 只出报告，列出问题与位置 | ❌ **禁止修改任何文件** |
| **阶段二 · 修复** | 按报告逐项修复 | ✅ 可以，但**必须先完成阶段一** |

**为什么必须分开**：边审边改会导致「修 A 引入新矛盾」，且事后无法区分「原问题」与「新问题」。

**默认只做阶段一。** 用户明确说「修掉」「帮我改」才进入阶段二。

---

## 二、两类审查，不能混

| 类型 | 判据 | 能否自动化 |
|---|---|---|
| **机械审查** | 客观可验证（链接存在、编号重复） | 基本可以 |
| **逻辑审查** | 需要读懂上下文（两个结论是否矛盾） | 不能，必须读 |

只做机械审查会漏掉结论矛盾；只做逻辑审查会漏掉编号断号。**两类都必须做。**

---

## 三、机械审查：五项

### 1. 双链完整性

提取所有 `[[...]]`（去掉 `#锚点` 与 `|别名`），检查是否对应实际存在的文件。

**注意**：代码块与行内代码里的 `[[...]]` 是误报，先剔除。

**同名文件歧义**：多个 `README.md` 时 `[[README]]` 解析不唯一——建议改用带路径写法或明确别名。

### 2. 编号唯一性与连续性

| 检查 | 例 |
|---|---|
| 重复定义 | 两个 `D-5` 含义不同 |
| 断号 | 有 `D-6` 和 `D-8`，无 `D-7` |
| 引用了未定义的编号 | 写「见 D-12」，索引里没有 |
| 两套编号混用 | `D1`（架构）与 `D-1`（决策）同时存在 |

### 3. 版本号映射

若采用「`y` 位绑里程碑」，检查三处是否一致：`AGENTS.md` 映射表、`ROADMAP.md` 映射表、各里程碑的 `version_range` 与门禁里的版本。

### 4. 文件路径引用

提取 `docs/xxx/yyy.md`、`xxx/NN-slug` 形式的路径，检查是否存在。

**要区分**：已存在文档的引用失效 → 真问题；未来文档的计划引用（「待落盘 `10-xxx`」）→ 正常，但需确认编号未被占用。

### 5. frontmatter 完整性

必需字段（`title` / `type` / `updated`）是否齐备；`type` 与 `status` 取值是否在 `AGENTS.md` 声明的枚举内。

---

## 四、逻辑审查：四项

### 1. 主题级矛盾（最高价值）

先列一张「被推翻过的关键结论」对照表（早期 → 最新），再全库搜索旧表述。**这一步能抓到的都是阻断级问题。**

### 2. 数字矛盾

同一参数多处出现时逐个核对：阈值不同、单位不一致（「3 天」vs「3 次」）、概念混淆（「调度条数」被当「投递条数」）。

### 3. 章节引用有效性

「见 §X.Y」「第 N 节」「[[文档]] §N」指向的章节是否仍存在。文档重构后章节号最容易失效。

### 4. 术语不一致

同一概念多种写法会让检索失效。原则：**概念层用中文，实现层用代码名；同一层级内只用一种。**

---

## 五、规范对齐（必做，不是可选）

核对「`AGENTS.md` 声明的规约」与「实际文档」是否一致：

| 检查 | 例 |
|---|---|
| 声明的必填小节 vs 实际 | AGENTS 要求里程碑有「风险与未决」，实际有几份缺？ |
| 声明的目录结构 vs 实际 | 有没有多出来的顶层目录 |
| 声明的标注体系 vs 实际用法 | AGENTS 说四档标注，文档里用的是旧的三档？ |
| 声明的覆盖率门禁 vs 各里程碑 | 数字是否被改写过 |

> 这一项常被当作「可选」而漏掉，结果是**规约与事实长期背离**。

---

## 六、分级与「什么才算问题」

| 级别 | 判据 | 处理 |
|---|---|---|
| **阻断级** | 结论直接矛盾、编号指向错误对象、按此实现会出错 | 必须修 |
| **建议级** | 表述陈旧、记法不统一、索引漏项 | 可批量修，可延后 |

### 一条关键判据：同层级内矛盾才算问题

**合法的层次差异**（不要当成 bug 去「修」）：

| 现象 | 为什么合法 |
|---|---|
| 调研报告保留旧结论 | 调研是**历史记录**，末尾有「对前序的修订」表；改正文会破坏可追溯性 |
| 决策文档记录「原方案被否」 | 决策记录的就是取舍过程 |
| 索引摘要与正文措辞不同 | 摘要是压缩，不是矛盾 |

**误把历史记录当 bug 去改，会造成更大混乱**——你会失去「当初为什么这么想」的证据。

---

## 七、产出物（必须落盘）

```
docs/reviews/R<N>-<slug>.md
```

- `R<N>`：审查记录编号，**与决策的 `D<N>` 分开**，不要抢号
- 用 `templates/review.md.tpl`
- 若还没有 `docs/reviews/`，创建它

报告至少包含：范围与方法 / 阻断级 / 建议级 / 登记但不修（含理由）/ 冻结基线 / 待办。

---

## 八、执行方式

### 分组并行

文档多时按职责拆 2–3 组：机械组、逻辑组、规范对齐组。

**单个 Agent 也可以顺序做完三组**——不必强制拆子任务。

### 给执行者的任务书要写明

- 审查范围（明确排除参考快照目录）
- 每条问题必须给 `文件路径:行号` 与原文片段
- **不允许修改文件**
- 若无问题，明确写「无问题」（避免「没查到」被当成「查了没有」）

### 可复用的机械检查手法

```bash
# 悬空双链（粗筛，需人工剔除代码块误报）
grep -roh '\[\[[^]]*\]\]' --include='*.md' . | sed 's/\[\[\([^]|#]*\).*/\1/' | sort -u

# 旧编号残留
grep -rn 'M[0-5] \|D-7\b' --include='*.md' .

# 标题层级与章节引用
grep -rn '见 §' --include='*.md' .
```

## 九、修复顺序（阶段二）

1. **先修阻断级**，一次修完再动建议级——否则边修边引入新矛盾
2. **同一主题的修改一次性做完**（改 A 结论，同时改引用它的 B、C）
3. **修完回归**：重跑机械审查，确认没有新的悬空链接

| 问题 | 修法 |
|---|---|
| 旧结论残留 | 改为最新结论；需保留历史则写「（已被 X 取代）」 |
| 编号冲突 | **后续文档整体顺延**，不要只改一处 |
| 两套编号混用 | 换掉其中一套的前缀（架构用 `A<N>`） |
| 数字不一致 | 统一到一个值，并注明「另一个是不同概念」 |
| 表名不一致 | 二选一，全文替换 |

---

## 十、冻结基线

审查通过后：

1. 落盘 `R<N>` 报告，写明「冻结含义：此后变更须走决策记录流程」
2. 提交 commit，信息里写清：审查范围 / 阻断级问题 / 关键结论变更
3. 在报告里列出「登记但不修」及理由，避免下次重复提出

---

## 十一、反模式

| 反模式 | 后果 |
|---|---|
| 边审边改 | 改 A 引入新矛盾，无法区分原问题与新问题 |
| 把历史记录当 bug 去改 | 丢失「当初为什么这么想」的证据 |
| 只做机械审查 | 链接全对，但结论互相矛盾——最致命 |
| 只做逻辑审查 | 编号断号、双链悬空累积 |
| 不给 `文件:行号` | 报告无法复核 |
| 「没查到」写成「无问题」 | 掩盖覆盖面缺口 |
| 冻结记录占用 D 编号 | 与真实决策抢号 |
| 审查报告不落盘 | 第二个人无法复核，下次重新查一遍 |

---

## 十二、自检

```
[ ] 明确当前是阶段一（只报告）还是阶段二（修复）
[ ] 机械五项全查（链接/编号/版本/路径/frontmatter）
[ ] 逻辑四项全查（矛盾/数字/章节/术语）
[ ] 规范对齐已做（AGENTS 声明 vs 实际）
[ ] 每个问题都有 文件:行号 + 原文
[ ] 区分了「同层级矛盾」与「合法的历史记录」
[ ] 报告已落盘 docs/reviews/R<N>-<slug>.md
[ ] 未修项已登记理由
```
