# eng-milestone · 里程碑规划与验收

里程碑的核心不是「列功能」，而是**回答两个二值问题**：能不能开工？算不算做完？

> 模板：`../../templates/milestone.md.tpl`。若宿主提供插件根路径变量，优先使用。

---

## 一、切分原则

**按「用户可感知的能力」切，不按「代码模块」切。**

| 好 | 坏 |
|---|---|
| 「能对话了」 | 「完成 LLM 适配层」 |
| 「记得住事了」 | 「接入记忆库」 |
| 「会挑时候提醒了」 | 「实现决策引擎」 |

判据：**每个里程碑结束时，必须能演示一个用户看得见的行为变化。** 不能演示的，说明它不是里程碑，是任务。

### 里程碑数量

- 4–8 个起步阶段为宜
- 每个里程碑控制在「1–3 周可完成」的量级
- 超过 8 个，说明粒度过细，考虑合并；少于 4 个，说明跨度过大，无法独立验收

---

## 二、文档九段结构

缺任何一段都不算完整里程碑文档。

| # | 段落 | 必须回答 | 常见缺陷 |
|---|---|---|---|
| 1 | **目标** | 一句话说清交付什么能力给用户 | 写成功能清单 |
| 2 | **非目标** | 明确不做什么 | 省略，导致范围蔓延 |
| 3 | **前置调研** | 内部：复用/改动/冲突/受哪些决策约束<br>外部：是否需要，需要则落盘调研文档 | 只写「需要调研」，不写结论 |
| 4 | **交付物** | 可勾选的清单，每条可验证 | 写「优化性能」这类不可验证项 |
| 5 | **数据模型变更** | 新增/修改的表与字段 | 漏写迁移影响 |
| 6 | **测试套件** | 单元 / 集成 / E2E / 故障注入 四层 | 只写「加测试」 |
| 7 | **验收门禁** | 可勾选、可判真伪 | 写「质量达标」 |
| 8 | **风险与未决** | 每条带处理方式 | 只列风险不给对策 |
| 9 | **验收记录** | 验收时填写实际数据 | 永远空着 |

---

## 三、前置调研是硬门禁

**这是本技能最重要的一条规则。**

> 每个里程碑在写第一行代码之前，必须完成前置调研并落盘。这是硬门禁，不可跳过。

### 内部调研（必做）

| 问题 | 为什么要问 |
|---|---|
| 复用哪些已有模块 | 避免重造 |
| 哪些接口需改动 | 预判回归风险 |
| 与既有设计的冲突点 | 提前暴露，而不是写到一半才发现 |
| 受哪些已落定决策约束 | 防止无意中推翻已定方案 |

### 外部调研（按需但必须判断）

**判据：如果需要对着某个官方文档或第三方代码「边看边写」，就属于必须调研。**

必须产出 `docs/research/NN-slug.md`，并满足：

- 每条结论带 `[官方]` / `[推断]` / `[待确认]` / `[未找到]` 标注
- `[官方]` 必须给链接
- 「待确认」项被显式列出，并标注「何时验证」
- 会阻塞实现的结论，单列到里程碑的「未决问题」并给出验证方式

> 调研协议细节见 `eng-research` 技能。

### 「能否开工」的判定

```
[ ] 内部调研四问全部有答案
[ ] 涉及外部平台/未验证假设的，调研文档已落盘
[ ] 阻塞项已解或已标注「以 PoC 验证」
[ ] 非目标已写且经用户确认
[ ] 数据模型变更已明确
```

**任何一项没打勾，就是不能开工。** 这时应当输出「阻塞原因 + 需要谁做什么」，而不是硬着头皮写。

## 四、验收门禁

### 覆盖率三档

| 层级 | 目标 | 说明 |
|---|---|---|
| 本里程碑 | ≥ **80%** | 新增/修改代码的行覆盖率 |
| 全局集成 | ≥ **75%** | 跨模块主链路端到端 |
| 核心纯函数 | **100%** 分支 | 决策/计算类无 IO 逻辑，没有理由低于 100% |

「达不到必须有记录」：若确无法达到，必须在验收记录写明原因与补偿措施（如手工回归清单），并由用户确认——**不允许静默放过**。

### 测试四层

```
tests/
├── unit/            # 纯函数、契约、映射
├── integration/     # 模块间链路
├── e2e/             # 进程级完整流程
└── fixtures/        # 固定样本（外部报文、桩响应、边界数据）
```

### 必须有的测试类型

| 类型 | 举例 |
|---|---|
| 契约测试 | 接口的所有实现跑同一套公共行为测试 |
| 故障注入 | 外部依赖超时/失败时的降级行为 |
| 幂等测试 | 同一操作重复执行只生效一次 |
| 隔离测试 | A 的数据不出现在 B 的结果里 |
| 回归测试 | 已修复的 bug 必须有对应测试 |

### 门禁写法要求

```
✅ [ ] 本里程碑测试覆盖率 ≥ 80%
✅ [ ] 隔离测试通过：A 的数据不出现在 B 的召回（一票否决）
❌ [ ] 代码质量良好
❌ [ ] 基本功能可用
```

**判据：换一个陌生人来，能不能客观判定这一项过没过。** 不能，就重写。

## 五、反模式

| 反模式 | 后果 |
|---|---|
| 里程碑里塞「顺便优化一下」 | 范围蔓延，永远无法验收 |
| 非目标写「暂不考虑」 | 等于没拒绝，下次还会提 |
| 门禁写「通过评审」 | 无法判定真伪 |
| 前置调研写「已调研」但无文档 | 无法复核，等于没做 |
| 验收记录永远空着 | 覆盖率门禁变成摆设 |
| 里程碑依赖未完成的其他里程碑 | 无法独立验收，应合并或重排 |

## 六、跨文档一致性

里程碑文档不是孤立的，必须与以下保持一致：

| 对象 | 必须一致 |
|---|---|
| `ROADMAP.md` | 里程碑编号、版本号、前置调研状态 |
| 架构文档 | 章节引用、约束编号（C1/C2…） |
| 决策索引 | 引用的 `D-xx` 编号含义必须与 ROADMAP 定义一致 |
| 其他里程碑 | 同一概念的表名/字段名/阈值 |

> 跨文档不一致是最常见的隐性 bug——**引用了错编号的约束，等于设计时就看错了前提**。开工前建议跑一次 `eng-audit`。

## 七、自检

```
[ ] 里程碑能演示一个用户可见的行为变化
[ ] 非目标已写，且每条带原因
[ ] 内部调研四问全部有答案
[ ] 涉及外部平台的调研文档已落盘（或已判定不需要）
[ ] 交付物每条可验证（不是「优化性能」这类）
[ ] 数据模型变更已明确
[ ] 测试四层都有内容，不是只写「加测试」
[ ] 门禁每条都能被判真伪
[ ] 引用的 D-xx / C-xx 编号含义与 ROADMAP、架构文档一致
```
