# eng-audit · 一致性与逻辑审查

文档超过 10 份后，人记得住「最新结论」，记不住「旧结论还残留在哪」。残留旧结论会以「引用错编号」「按废弃方案设计」的方式变成真实 bug。

> 模板：`../../templates/review.md.tpl`；产物路径见 §七。

---

## 一、两个阶段，不要混（本技能最容易做错的地方）

| 阶段 | 做什么 | 允许改文件吗 |
|---|---|---|
| **阶段一 · 审查** | 只出报告，列问题与位置 | ❌ **禁止修改任何文件** |
| **阶段二 · 修复** | 按报告逐项修复 | ✅ 可以，但**必须先完成阶段一** |

**为什么分开**：边审边改会「修 A 引入新矛盾」，且事后无法区分原问题与新问题。
**默认只做阶段一**；用户明确说「修掉」「帮我改」才进入阶段二。

---

## 二、两类审查，不能混

| 类型 | 判据 | 能否自动化 |
|---|---|---|
| **机械审查** | 客观可验证（链接存在、编号重复） | 基本可以 |
| **逻辑审查** | 需要读懂上下文（结论是否矛盾） | 不能，必须读 |

只做机械漏结论矛盾；只做逻辑漏编号断号。**两类都必须做。**

---

## 三、机械审查：五项

1. **双链完整性**：提取 `[[...]]`（去 `#锚点` 与 `|别名`），核对目标文件存在。**代码块与行内代码里的 `[[...]]` 是误报，先剔除**；多个同名文件（如多个 README）时 `[[README]]` 解析不唯一，改带路径写法或别名
2. **编号唯一性与连续性**：重复定义、断号、引用未定义编号、两套编号混用（`D1` vs `D-1`）
3. **版本号映射**：`y` 位绑里程碑时，核对 `AGENTS.md` 映射表、`ROADMAP.md` 映射表、各里程碑 `version_range` 三处一致
4. **文件路径引用**：提取 `docs/xxx/yyy.md` 类路径核对存在。已存在文档的引用失效 = 真问题；未来文档的计划引用 = 正常，但需确认编号未占用
5. **frontmatter 完整性**：`title` / `type` / `updated` 齐备；`type`、`status` 取值在 `AGENTS.md` 声明的枚举内

**可选脚本加速**：`scripts/mechanical-check.sh [目录]`——一次跑完五项粗筛（已剔除代码块误报，输出 `文件:行号`，版本映射仅提取行供人工比对）。无脚本环境按上文手法逐项手工 grep。

---

## 四、逻辑审查：四项

1. **主题级矛盾**（最高价值）：先列「被推翻过的关键结论」对照表（早期 → 最新），再全库搜旧表述——抓到的都是阻断级
2. **数字矛盾**：同一参数多处出现逐一核对：阈值不同、单位不一致（「3 天」vs「3 次」）、概念混淆（「调度条数」当「投递条数」）
3. **章节引用有效性**：「见 §X.Y」「第 N 节」「`[[文档]]` §N」指向的章节是否仍在——重构后章节号最易失效
4. **术语不一致**：同一概念多种写法让检索失效。原则：**概念层用中文，实现层用代码名；同一层级内只用一种**

---

## 五、规范对齐（必做，不是可选）

核对「`AGENTS.md` 声明的规约」与「实际文档」：

| 检查 | 例 |
|---|---|
| 声明的必填小节 vs 实际 | AGENTS 要求里程碑有「风险与未决」，几份缺？ |
| 声明的目录结构 vs 实际 | 有没有多出来的顶层目录 |
| 声明的标注体系 vs 实际用法 | AGENTS 说四档标注，文档里还是旧三档？ |
| 声明的覆盖率门禁 vs 各里程碑 | 数字是否被改写 |

> 这一项常被当「可选」漏掉，结果是**规约与事实长期背离**。

---

## 六、分级与「什么才算问题」

| 级别 | 判据 | 处理 |
|---|---|---|
| **阻断级** | 结论直接矛盾、编号指向错误对象、按此实现会出错 | 必须修 |
| **建议级** | 表述陈旧、记法不统一、索引漏项 | 可批量修，可延后 |

**关键判据：同层级内矛盾才算问题。** 合法的层次差异不要当 bug 修：

| 现象 | 为什么合法 |
|---|---|
| 调研报告保留旧结论 | 调研是历史记录，末尾有修订表；改正文破坏可追溯性 |
| 决策文档记录「原方案被否」 | 决策记录的就是取舍过程 |
| 索引摘要与正文措辞不同 | 摘要是压缩，不是矛盾 |

**误把历史记录当 bug 改，会失去「当初为什么这么想」的证据。**

---

## 七、产出物（必须落盘）

```
docs/reviews/R<N>-<slug>.md
```

- `R<N>` 与决策的 `D<N>` 分开，不抢号（预检用 `eng-bootstrap` 的 `scripts/number-inventory.sh`）
- 用 `templates/review.md.tpl`；还没有 `docs/reviews/` 就创建
- 报告至少含：范围与方法 / 阻断级 / 建议级 / 登记但不修（含理由）/ 冻结基线 / 待办

---

## 八、执行方式

- 文档多时按职责拆 2–3 组（机械/逻辑/规范对齐）；单个 Agent 顺序做完也可以，不必强制拆
- **给执行者的任务书**：审查范围（明确排除参考快照目录）；每条问题给 `文件路径:行号` + 原文片段；**不允许修改文件**；无问题就明确写「无问题」（避免「没查到」被当成「查了没有」）

---

## 九、修复顺序（阶段二）

1. **先修阻断级**，一次修完再动建议级
2. **同一主题的修改一次性做完**（改 A 结论，同时改引用它的 B、C）
3. **修完回归**：重跑机械审查，确认没有新悬空链接

| 问题 | 修法 |
|---|---|
| 旧结论残留 | 改为最新结论；需保留历史则写「（已被 X 取代）」 |
| 编号冲突 | 后续文档整体顺延，不只改一处 |
| 两套编号混用 | 换掉其中一套的前缀（架构用 `A<N>`） |
| 数字不一致 | 统一到一个值，注明「另一个是不同概念」 |
| 表名不一致 | 二选一，全文替换 |

---

## 十、冻结基线

1. 落盘 `R<N>` 报告，写明「冻结含义：此后变更须走决策记录流程」
2. 提交 commit：信息写清审查范围 / 阻断级问题 / 关键结论变更
3. 报告里列「登记但不修」及理由，避免下次重复提出

---

## 十一、反模式

| 反模式 | 后果 |
|---|---|
| 边审边改 | 改 A 引入新矛盾，无法区分原问题与新问题 |
| 把历史记录当 bug 去改 | 丢失「当初为什么这么想」的证据 |
| 只做机械审查 | 链接全对但结论互相矛盾——最致命 |
| 只做逻辑审查 | 编号断号、双链悬空累积 |
| 不给 `文件:行号` | 报告无法复核 |
| 「没查到」写成「无问题」 | 掩盖覆盖面缺口 |
| 冻结记录占用 D 编号 | 与真实决策抢号 |
| 审查报告不落盘 | 第二个人无法复核，下次重查一遍 |

---

## 十二、自检

```
[ ] 明确当前是阶段一（只报告）还是阶段二（修复）
[ ] 机械五项全查（链接/编号/版本/路径/frontmatter）
[ ] 逻辑四项全查（矛盾/数字/章节/术语）
[ ] 规范对齐已做（AGENTS 声明 vs 实际）
[ ] 每个问题都有 文件:行号 + 原文
[ ] 区分了「同层级矛盾」与「合法的历史记录」
[ ] 报告已落盘 docs/reviews/R<N>-<slug>.md
[ ] 未修项已登记理由
```
