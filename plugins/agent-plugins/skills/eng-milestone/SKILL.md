# eng-milestone · 里程碑规划与验收

里程碑要回答两个二值问题：**能不能开工？算不算做完？**

> 模板：`../../templates/milestone.md.tpl`。若宿主提供插件根路径变量，优先使用。

---

## 一、动手前先做三件事

| # | 动作 | 找不到怎么办 |
|---|---|---|
| 1 | 读 `ROADMAP.md`，拿到**本里程碑编号**与已有里程碑的命名 | 没有 ROADMAP → 先 `eng-bootstrap` |
| 2 | 看已有里程碑的 `slug` 风格，保持一致 | 无先例则用短横线小写英文 |
| 3 | 确认**上游架构文档**是否存在（要引用 `C<NN>` 约束） | 没有架构 → 先 `eng-architecture`，否则约束只能靠猜 |

### 产物路径与命名（必须遵守）

```
docs/milestones/M<NN>-<slug>.md
```

- `M<NN>`：**补零两位**，与 ROADMAP 一致（`M01`、`M07`）
- `<slug>`：短横线小写英文，≤32 字符，与标题语义对应；**中文标题也要配英文 slug**
- 同目录索引在 `docs/milestones/README.md`

> 注意两套编号**空间隔离**：里程碑用 `M<NN>`，调研用 `NN`。不要写成 `02-xxx.md`。

## 二、切分原则

**按「用户可感知的能力」切，不按「代码模块」切。**

| 好 | 坏 |
|---|---|
| 「能对话了」 | 「完成 LLM 适配层」 |
| 「记得住事了」 | 「接入记忆库」 |

判据：**每个里程碑结束时，必须能独立演示或独立度量一个变化。**
不能演示也不能度量的，说明它不是里程碑，是任务。

> 「可度量」是为体验类改动留的口子：如「记忆隔离」「疲劳降频」，验收靠测试断言而非界面演示。

### 依赖关系要声明，不要回避

里程碑之间有依赖是**常态**，不是错误。做法：

1. 在文档里写一节「依赖」：本里程碑依赖哪些已完成成果
2. 在 ROADMAP 里标出**哪批可以并行开工**（如「M01–M05 互不依赖，M06 依赖 PoC」）
3. 只有**循环依赖**才需要重排或合并

## 三、九段结构

缺任何一段都不算完整。

| # | 段落 | 必须回答 |
|---|---|---|
| 1 | 目标 | 一句话，可演示或可度量 |
| 2 | 非目标 | 明确不做什么，每条带原因 |
| 3 | 前置调研 | 内部四问 + 外部调研（需要/不需要都写理由） |
| 4 | 交付物 | 可勾选、可验证 |
| 5 | 数据模型变更 | 新增/修改的表与字段 |
| 6 | 测试套件 | 单元 / 集成 / E2E / 故障注入 |
| 7 | 验收门禁 | 可判真伪，按阶段分档（见 §五） |
| 8 | 风险与未决 | 每条带处理方式 |
| 9 | 验收记录 | **验收时填写**（见 §六） |

---

## 四、前置调研是硬门禁

> 前置调研没落盘，**不得开始写这个里程碑的代码，也不得把里程碑标为可开工**。

### 内部调研：四问 + 证据

| 问题 | 要求 |
|---|---|
| 复用哪些已有模块 | **必须给出模块名或文件路径**，不能写「复用现有架构」 |
| 哪些接口需改动 | 给出接口名 |
| 与既有设计的冲突点 | 给出涉及的 `C<NN>` 或章节号 |
| 受哪些已落定决策约束 | 给出 `D-xx` 编号 |

**判据**：把四行贴给第三方，他能否据此判断影响面。不能，就是空话。

### 外部调研

**判据**：需要对着某个官方文档或第三方代码「边看边写」→ 必须调研。

产出 `docs/research/NN-<slug>.md`，四档标注齐全（详见 `eng-research`）。

### 能否开工的判定

```
[ ] 内部四问每行都有具体模块名/接口名/编号
[ ] 外部调研已落盘，或已写明「不需要」及理由
[ ] 阻塞项已解，或已标注验证方式（PoC / 实测）
[ ] 非目标已写，且经用户确认
[ ] 数据模型变更已明确
```

**没打勾就不能开工。** 此时应输出「卡在哪 + 需要谁做什么」，而不是硬写。

## 五、验收门禁：按阶段分档

同一套门禁在「还没有代码」时无法判真伪，所以分两档。

### 文档阶段（本里程碑尚未产出代码）

```
[ ] 九段结构完整
[ ] 内部调研四问带具体证据
[ ] 外部调研已落盘或已判定不需要
[ ] 交付物每条可验证
[ ] 数据模型变更已明确
[ ] 覆盖率门禁标为 N/A（不写「待达标」）
```

### 编码阶段（已有代码交付）

```
[ ] 覆盖率达标（阈值以 AGENTS.md §五 为唯一权威）
[ ] 测试四层齐备：单元 / 集成 / E2E / 故障注入
[ ] 无新增未记录的技术债
[ ] ROADMAP + CHANGELOG 已同步，版本已按规则更新
[ ] 用户已确认验收
```

> **覆盖率不写具体数字**，只写「以 `AGENTS.md` 为准」。数字分散多处必然漂移。

### 测试四层（固定，不要自创）

| 层 | 内容 | 常见错误 |
|---|---|---|
| 单元 | 纯函数、契约、映射 | — |
| 集成 | 模块间链路 | — |
| E2E | 进程级完整流程 | — |
| 故障注入 | 外部依赖失败时的降级 | 常被漏掉，但它才是「会不会崩」的关键 |

`fixtures/` 是**素材目录**，不是测试层，不要列进四层。

### 门禁写法要求

```
✅ [ ] 隔离测试通过：A 的数据不出现在 B 的结果（一票否决）
✅ [ ] 若已进入编码阶段：覆盖率 ≥ AGENTS 设定值
❌ [ ] 代码质量良好
❌ [ ] 本阶段覆盖率达标
```

判据：**换一个陌生人来，能否客观判定过没过。**

## 六、验收动作（谁在什么时候做）

里程碑完成时，**由执行者主动发起**，不等别人来问：

1. 逐条打勾门禁；不达标的写明原因与补偿措施
2. 填写「验收记录」：实际覆盖率、未达标项、遗留技术债
3. 打 `x.y.0` tag
4. 更新 ROADMAP 状态行、把 CHANGELOG 的 `[Unreleased]` 切到 `[x.y.0]`
5. 若推翻了既有结论 → 走 `eng-research` 的「推翻与回写」清单

> 「验收记录」空着**不是缺陷**——只要还没验收。缺陷是**没有规定谁在什么时点填**。

## 七、反模式

| 反模式 | 后果 |
|---|---|
| 里程碑里塞「顺便优化一下」 | 永远无法验收 |
| 非目标写「暂不考虑」 | 等于没拒绝，下次还会提 |
| 门禁写「通过评审」 | 无法判真伪 |
| 前置调研只有「已确认」四个字 | 无法复核，等于没做 |
| 覆盖率数字写在四处 | 必然漂移 |
| 循环依赖不处理 | 两个里程碑都开不了工 |
| 把 `fixtures/` 当成测试层 | 故障注入被漏掉 |

## 八、自检

```
[ ] 产物路径符合 docs/milestones/M<NN>-<slug>.md
[ ] 已读 ROADMAP，编号与命名与既有里程碑一致
[ ] 目标可演示或可度量
[ ] 非目标每条带原因
[ ] 内部四问带具体模块名/接口名/编号
[ ] 外部调研已落盘或已判定不需要（含理由）
[ ] 交付物无「优化性能」这类不可验证项
[ ] 测试四层齐备（故障注入未漏）
[ ] 覆盖率门禁写「以 AGENTS 为准」，未写死数字
[ ] 门禁每条可判真伪，且已按阶段分档
[ ] 引用的 C<NN> / D-xx 含义与架构文档、ROADMAP 一致
```
