# eng-audit · 一致性与逻辑审查

**为什么需要这个技能**：文档超过 10 份后，人会记住「最新结论」，但记不住「旧结论还残留在哪」。而残留的旧结论会以「引用错了编号」「按废弃方案设计」的方式变成真实 bug。

---

## 一、两类审查，不能混

| 类型 | 判据 | 能否自动化 |
|---|---|---|
| **机械审查** | 客观可验证（链接是否存在、编号是否重复） | 基本可以 |
| **逻辑审查** | 需要读懂上下文（两个结论是否矛盾） | 不能，必须读 |

**两类都必须做**。只做机械审查会漏掉结论矛盾；只做逻辑审查会漏掉编号断号。

---

## 二、机械审查：五项

### 1. 双链完整性

提取所有 `[[...]]`（去掉 `#锚点` 与 `|别名`），检查是否对应实际存在的文件。

**注意**：代码块与行内代码里的 `[[...]]` 是误报，要先剔除。

**同名文件歧义**：多个 `README.md` 时，`[[README]]` 解析不唯一——建议改用带路径的写法或明确别名。

### 2. 编号唯一性与连续性

| 检查 | 例 |
|---|---|
| 重复定义 | 两个 `D-5` 含义不同 |
| 断号 | 有 `D-6` 和 `D-8`，无 `D-7` |
| 引用了未定义的编号 | 文档写「见 D-12」，索引里没有 |
| 两套编号混用 | `D1`（架构）与 `D-1`（决策）同时存在 |

### 3. 版本号映射

若项目采用「`y` 位绑里程碑」，检查三处是否一致：

- `AGENTS.md` 的映射表
- `ROADMAP.md` 的映射表
- 各里程碑文档的 `version_range` 与验收门禁里的版本

### 4. 文件路径引用

提取所有 `docs/xxx/yyy.md`、`xxx/NN-slug` 形式的路径，检查是否存在。

**要区分**：
- **已存在文档的引用失效** → 真问题
- **未来文档的计划引用**（如「待落盘 `10-xxx`」） → 正常，但需确认编号未被占用

### 5. frontmatter 完整性

| 检查 | 说明 |
|---|---|
| 必需字段 | 至少 `title` / `type` / `updated` |
| `type` 取值合法 | 与 AGENTS 里声明的枚举一致 |
| `status` 取值合法 | 同上（`draft` / `active` / `accepted` / `superseded` …） |

---

## 三、逻辑审查：四项

### 1. 主题级矛盾（最高价值）

**做法**：先列出项目里被推翻过的关键结论（做一张「早期 → 最新」对照表），然后全库搜索旧表述。

例：

| 主题 | 早期结论 | 最新结论 |
|---|---|---|
| 某平台能否做 X | 「不能」 | 「能，走 Y 通道」 |
| 某策略 | 「降级为可选」 | 「升级为核心」 |

**这一步能抓到的都是阻断级问题。**

### 2. 数字矛盾

同一参数在多处出现时，逐个核对：

- 同一阈值在不同文档里不同（如日上限 12 / 20 / 3 并存）
- 单位不一致（「连续 3 天」vs「连续 3 次」）
- 概念混淆（「调度条数上限」被当成「投递条数上限」用）

**做法**：把关键数字列成表，标注每个数字出现的所有位置。

### 3. 章节引用有效性

检查「见 §X.Y」「第 N 节」「[[文档]] §N」指向的章节是否仍存在。文档重构后章节号最容易失效。

### 4. 术语不一致

同一概念多种写法会导致检索失效与理解偏差。常见：

| 概念 | 可能的不同写法 |
|---|---|
| 会话标识 | 会话键 / `session_key` / `sessionKey` |
| 通道 | 通道 / 渠道 / Channel / adapter |
| 投递 | 投递 / 推送 / notify / Deliver |

**原则**：概念层用中文，实现层用代码名；同一层级内只用一种。

---

## 四、分级与「什么才算问题」

### 分级

| 级别 | 判据 | 处理 |
|---|---|---|
| **阻断级** | 结论直接矛盾、编号指向错误对象、按此实现会出错 | 必须修，修完才能继续 |
| **建议级** | 表述陈旧、记法不统一、索引漏项 | 可批量修，可延后 |

### 一条关键判据：同层级内矛盾才算问题

**合法的层次差异**（不要当成 bug 去"修"）：

| 现象 | 为什么合法 |
|---|---|
| 调研报告保留旧结论 | 调研是**历史记录**，每份末尾有「对前序的修订」表；改正文会破坏可追溯性 |
| 决策文档记录「原方案被否」 | 决策记录的就是取舍过程 |
| 索引摘要与正文措辞不同 | 摘要是压缩，不是矛盾 |

**只有同一层级内自相矛盾，才需要修。** 误把历史记录当 bug 去改，会造成更大的混乱——你会失去「当初为什么这么想」的证据。

---

## 五、执行方式

### 分组并行

文档多时，按职责拆成 2–3 组并行：

| 组 | 负责 | 输出 |
|---|---|---|
| A | 机械审查（链接/编号/版本/路径/frontmatter） | 问题清单 + 文件:行 |
| B | 逻辑审查（矛盾/数字/章节/术语） | 矛盾清单 + 原文片段 |
| C（可选） | 规范对齐（AGENTS 声明 vs 实际文档） | 偏差清单 |

### 任务书必须写明

- 审查范围（明确排除参考快照目录）
- 每条问题必须给 `文件路径:行号` 与原文片段
- **不允许修改文件**，只出报告
- 若无问题，明确写「无问题」（避免「没查到」被当成「查了没有」）

---

## 六、修复顺序

1. **先修阻断级**，一次修完再动建议级——否则边修边引入新矛盾
2. **同一主题的修改一次性做完**（改 A 文档的结论，同时改引用它的 B、C）
3. **修完做一次回归验证**：重跑机械审查，确认没有新的悬空链接

### 常见修复手法

| 问题 | 修法 |
|---|---|
| 旧结论残留 | 直接改为最新结论；若需保留历史，改写为「（已被 X 取代）」 |
| 编号冲突 | **后续文档整体顺延**，不要只改一处 |
| 两套编号混用 | 换掉其中一套的字母前缀（如架构用 `A1`） |
| 数字不一致 | 统一到一个值，并注明「另一个数字是不同概念」 |
| 表名不一致 | 二选一，全文替换 |

---

## 七、冻结基线

审查通过后做一次冻结，把当前状态固化为基线：

1. 写一份**校对冻结记录**（属于决策记录的一种）：列出发现数、修复数、**登记但不修**的项目及理由
2. 提交 commit，信息里写清：审查范围 / 阻断级问题 / 关键结论变更
3. 在冻结记录里写明「冻结含义」：此后变更须走决策记录流程

### commit 信息要求

```
<type>: <一句话主题>

<为什么做这次提交——背景与目的>

<分点说明做了什么，覆盖哪些阶段/模块>

<关键结论或变更，便于日后检索>

<排除项说明（如 _refs/ 不入库）>
```

**不要用一句话概括整个提交。** 半年后的自己只会看 commit 历史，正文比主题更重要。

---

## 八、自检

```
[ ] 机械五项全查（链接/编号/版本/路径/frontmatter）
[ ] 逻辑四项全查（矛盾/数字/章节/术语）
[ ] 每个问题都有 文件:行号 + 原文
[ ] 区分了「同层级矛盾」与「合法的历史记录」
[ ] 阻断级全部修复并回归验证
[ ] 未修的项已登记理由
[ ] 冻结记录与 commit 已落盘
```

---

## 九、审查自身的反模式

| 反模式 | 后果 |
|---|---|
| 把历史记录当 bug 去改 | 丢失「当初为什么这么想」的证据，比不改更糟 |
| 只做机械审查 | 链接全对，但结论互相矛盾——这类问题最致命 |
| 只做逻辑审查 | 编号断号、双链悬空累积，检索逐步失效 |
| 边审边改 | 改 A 引入新矛盾，且无法区分「原问题」与「新问题」 |
| 不给 `文件:行号` | 报告无法复核，执行者要重新定位 |
| 「没查到」写成「无问题」 | 掩盖了覆盖面缺口 |
| 一次改完所有建议级 | 噪声太大，阻断级淹没在里面 |
