# eng-architecture · 架构规格

架构文档回答一个问题：**这个系统长什么样，哪些是不能违反的。**

它是最容易被跳过、也最容易失控的一类文档——唯一被下游反复引用（约束编号、章节号、表结构）的产物。

> 模板：`../../templates/architecture.md.tpl`；目录索引用 `../../templates/architecture-index.md.tpl`。宿主提供插件根路径变量时优先使用。

---

## 一、三类文档的边界（先分清，否则互相污染）

| 文档 | 写什么 | **不写**什么 |
|---|---|---|
| **调研**（`docs/research/`） | 证据、来源、待确认项 | 「我们决定用 X」 |
| **决策**（`docs/decisions/`） | 取舍、理由、放弃的代价 | 字段名、接口签名 |
| **架构**（`docs/architecture/`） | 规格：约束、模块、数据模型、接口契约 | 「为什么选它」（那是决策） |

**判据**：架构文档里出现「因为 X 比 Y 便宜」→ 属于决策，改成一句双链指过去。

---

## 二、两个编号体系，不要混

| 前缀 | 含义 | 例子 |
|---|---|---|
| **`A<N>`** | 架构**文档**编号 | `A1 架构定稿`、`A2 数据模型` |
| **`C<N>`** | 架构**内部约束**编号 | `C1 namespace 隔离`、`C5 单聊无 chatid` |

两条硬规则：

1. **文档编号用 `A`，不要用 `D`**——`D` 已被决策占用
2. **`C<N>` 一旦分配，不得改变含义**——里程碑会引用它；要改含义就新开 `C<N+1>` 并标注旧号废弃

## 三、约束表（架构文档的核心）

每个约束必须四列齐全：

| # | 约束 | 类型 | 来源 |
|---|---|---|---|
| C1 | <一句话，可判真伪的事实> | **客观** | `[[调研编号]]` |
| C7 | <一句话> | **工程** | 用户决策（`D-xx`） |

| 类型 | 含义 | 可协商 |
|---|---|---|
| **客观** | 平台/依赖库的既成事实 | ❌ 只能适配 |
| **工程** | 我们自己的选择 | ✅ 可经新决策推翻 |

**混淆的代价**：工程选择写成客观约束 → 几个月后没人敢改；客观限制当工程选择 → 一改就撞墙。

**来源只能三选一**：某份调研的编号（`[官方]` 级证据）/ 某个决策编号 / 「项目定位」（如「5–20 人自用」）。没有来源的约束等于拍脑袋。

---

## 四、文档结构（约束在最前）

```markdown
## 一、设计约束（客观/工程分类，带来源）
## 二、模块图（分层 + 箭头方向）
## 三、进程与部署模型
## 四、数据模型（DDL；关键索引与约束）
## 五、接口契约（跨模块输入输出）
## 六、关键流程（时序或状态机）
## 七、明确不做的（架构级）
## 八、校准记录（后续追加，见 §六）
```

**顺序理由**：读者只有先知道「什么不能动」，后面的一切才可读。

---

## 五、数据模型写法

- **DDL 要能直接跑**，不是伪代码
- **唯一索引必须写出来**——它是隔离与幂等的实现，不是优化
- **每张表标注隔离维度**（按用户/租户/全局）——最容易埋雷的地方
- 字段级「为什么」写成一句话行内注释

**反例**：只画 ER 图不给 DDL——ER 图看不出唯一约束，而唯一约束往往就是安全边界。

---

## 六、演进：追加校准节，不要重写

1. 追加一节 `## <N>、<阶段> 校准（vX.Y）`：原假设是什么、为什么错、改成什么
2. frontmatter `status` 升版：`draft-v1` → `draft-v1.3`

> 理由：里程碑和决策引用的是「当时的架构」，重写会让历史引用悬空；追加保留可追溯。

**校准累积到正文自相矛盾时**才整体重写，旧版留档（`status: superseded`）。

## 七、架构索引

`docs/architecture/README.md`（用 `architecture-index.md.tpl`）至少含：

| 内容 | 为什么 |
|---|---|
| 文档清单（编号/标题/回答什么问题/状态） | 知道有几份、各管什么 |
| **阅读顺序** | 架构文档有依赖，乱读会误解 |
| **依赖方向图** | 防循环引用 |
| **约束索引**（`C<N>` → 出处） | 里程碑引用时可校验 |

## 八、反模式

| 反模式 | 后果 |
|---|---|
| 约束不带来源 | 无法判断能否推翻，成了「祖传规矩」 |
| 把决策理由写进架构 | 两份文档各存一半，必然漂移 |
| 重写而非追加 | 历史引用全部悬空 |
| 只画 ER 图不给 DDL | 唯一约束丢失，隔离边界说不清 |
| `A`/`C`/`D` 编号混用 | 「D1 是架构还是决策」无法回答 |
| 架构文档不设索引 | 三份以上找不到入口，没人发现依赖成环 |
| 约束写「应尽量…」 | 不可判真伪，等于没约束 |

## 九、自检

```
[ ] 每条约束都有「类型（客观/工程）」与「来源」
[ ] 约束表述可判真伪（没有「尽量」「适当」）
[ ] 数据模型给了可直接跑的 DDL，标出唯一索引与隔离维度
[ ] 文档编号用 A<N>，未与决策 D<N> 混用
[ ] C<N> 编号无重复、无改义
[ ] 修正以「追加校准节 + 升 draft-vN」完成，未重写正文
[ ] docs/architecture/README.md 有清单、阅读顺序、依赖方向
[ ] 架构里不出现「为什么选它」（已用双链指过去）
```
