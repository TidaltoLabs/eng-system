# eng-research · 调研协议

调研的目的不是「收集资料」，而是**让下一个决策有据可依**。

> 模板：`../../templates/research.md.tpl`。宿主提供插件根路径变量时优先使用。

---

## 一、来源标注（强制）

每一句结论都必须能归入四档之一：

| 标注 | 含义 | 要求 |
|---|---|---|
| `[官方]` | 官方文档/源码原文可支持 | **必须给链接 + 引用原文** |
| `[推断]` | 基于原文结构的工程判断 | 必须说明推理链 |
| `[待确认]` | 官方未覆盖，需实测 | 必须写「何时验证、怎么验证」 |
| `[未找到]` | 查过但无此内容 | 说明查了哪些来源（≠「不存在」） |

**为什么不砍成「可信/不可信」**：`[推断]` 不是缺点——大量工程结论只能靠推断，问题在于不标注；`[未找到]` 是给下一个人省重复劳动。

---

## 二、质量标准

**唯一标准：结论能直接支撑一个具体决策。**

| 合格 | 不合格 |
|---|---|
| 「X 不支持 A，因此只能走 B；代价是 C」 | 「X 功能丰富，生态活跃」 |
| 「官方原文写『5 秒内必须响应』，同步调 LLM 必然超时」 | 「需要注意响应时间」 |
| 「三份存档 + 线上页共六处一致，可信度中高」 | 「据网上说……」 |

三条硬要求：

1. **给证据不给印象**：引用原文、给 `file:line`、给 Wayback 链接，不转述二手说法
2. **区分「历史结论」与「当前现状」**：带发布/核实日期
3. **必须有「对前序的修订」一节**：推翻过任何判断就明写推翻了什么、为什么

## 三、五类常见谬误（反模式，都实际踩过）

| # | 谬误 | 判据 / 正确做法 |
|---|---|---|
| ① | 把「没人做」当成「不该做」 | 「没人实现」是市场信号不是价值判断。先问为什么没人做：技术不可行？成本过高？还是需求真实但没人满足——只有前两者才构成「不该做」 |
| ② | 把过期文档当现状 | 核实页面更新时间；冲突时用 Wayback 差分；官方静默改文档必须明写「无官方公告」，不包装成官方承诺 |
| ③ | 把推断写成结论 | 结论区只放已验证事实；推断单独成节并标注推理依据 |
| ④ | 资料汇编冒充调研 | 判据：读完不知道该选哪个方案 = 文献综述不是调研 |
| ⑤ | 忽略平台外约束 | 每个候选核实四维：**能力 / 门槛 / 成本 / 合规**（资质、价格、上架、违规风险） |

## 四、报告结构

```markdown
---
title: <阶段> · <主题>
type: research-report
status: completed
updated: YYYY-MM-DD
related: ["[[相关文档]]"]
---

# NN · <主题>

> 方法：<取证手段；数据快照日期>

## 零、结论（先给答案）
## 一、<主体一>
## 二、<主体二>
## 三、对前序的修订
## 四、待确认
```

**要求**：结论放最前，证据居中，修订与待确认放最后。读者 30 秒内知道答案，再决定要不要读细节。

## 五、多轮调研的编号与留痕

- 编号顺延：`docs/research/01-…`、`02-…`，**不得复用已占用编号**（预检用 `eng-bootstrap` 技能目录下的 `scripts/number-inventory.sh`）
- 每轮独立成文，**不修改历史报告的论证部分**；推翻结论写进新报告的「对前序的修订」表
- `docs/research/README.md` 是**调研索引的唯一权威**，五列：编号 / 文档 / 阶段 / 状态 / 一句话结论

> 保留错误的历史报告是为了可追溯：半年后有人问「当初为什么这么定」，要能看到当时的证据与推理。

### 事实性错误 vs 结论性推翻（两种处理，不要混）

| 情况 | 处理 | 例 |
|---|---|---|
| **事实性错误**（数字错、字段名错、链接失效） | **就地改**，修订表记一行 | `40184001` → `40054004` |
| **结论性推翻**（判断反了、方案被否） | **不改旧正文**，新报告修订表写明 | 「微信不能主动推送」→「能，走某通道」 |

**判据**：改完之后，旧的推理链是否还成立。成立就地改；不成立就留痕。

## 六、推翻之后要改哪些文件（fan-out 清单）

一条结论被推翻，受影响的不止调研本身。**按顺序过一遍，漏一步就留下阻断级矛盾**：

```
① 新调研的「对前序的修订」表        ← 记录推翻
② 历史调研正文                      ← 只改事实性错误，结论性不动
③ 架构文档                          ← 追加「校准」节，status 升 draft-vN
④ 决策记录                          ← 草稿期原地改；已冻结则标 superseded
⑤ ROADMAP 的决策索引 / 阶段摘要      ← 旧条目标 🔁 并注明被谁取代
⑥ 受影响里程碑的非目标 / 交付物 / 门禁
⑦ CHANGELOG                         ← 记一条「变更」
⑧ 各索引的一句话结论                 ← 摘要必须与正文一致
```

**判据**：改完后全库搜索旧结论关键词，应只出现在「修订记录」里。
可选脚本加速：本技能目录下的 `scripts/keyword-residue.sh <旧结论关键词>…`——剔除代码块与留痕行后报告残留位置；无脚本环境手工 `grep -rn '<关键词>' --include='*.md' .` 后人工剔除留痕行。

## 七、派生子任务时怎么写任务书

| 必须写清 | 为什么 |
|---|---|
| 要核实的**具体断言**（越具体越好） | 否则会得到一篇泛泛综述 |
| 要求给出 `file:line` 或链接 | 否则无法复核 |
| 要求标注四档来源 | 否则推断会被当成结论 |
| 要求「查不到就说查不到」 | 否则会被编造填补 |
| 说明哪些结论会决定什么 | 执行者才知道优先级 |

**明确禁止项也要写进去**，如：「禁止编造清单字段名和目录路径」「不要把营销文案当现状」。

## 八、自检清单

```
[ ] 结论区每条都能直接支撑一个决策
[ ] 每个 [官方] 都有链接与原文引用
[ ] 每个 [待确认] 都写了「何时、如何验证」
[ ] 有「对前序的修订」一节（若本次推翻过任何结论）
[ ] 核实了页面/文档的更新时间
[ ] 每个候选覆盖「能力 / 门槛 / 成本 / 合规」四维
[ ] 没有把「没人做」写成「不该做」
[ ] 新增编号未与既有编号冲突
```
