# eng-bootstrap · 工程骨架引导

一次性解决三件事：**这个项目不做什么**、**版本号怎么涨**、**什么算完工**。

> 模板位于本技能目录上两级的 `templates/`（即插件根目录）。若宿主提供插件根路径变量（如 `${CLAUDE_PLUGIN_ROOT}`），优先使用它。
> `AGENTS.md.tpl` / `ROADMAP.md.tpl` / `CHANGELOG.md.tpl` / `README.md.tpl` 为基础模板；`milestone.md.tpl` / `research.md.tpl` / `decision.md.tpl` 由其它技能使用。

---

## 一、先问，不要假设

**在写任何文件之前，必须先向用户确认以下四项。** 缺一项就停下来问。

| # | 必问 | 为什么不能猜 |
|---|---|---|
| 1 | **能力边界**：这个项目**明确不做**什么 | 「不做什么」是唯一有效的防蔓延手段；猜错等于埋雷 |
| 2 | **规模画像**：单人/小团队/多租户；用户量级；是否对外 | 决定要不要多进程、要不要权限体系、要不要计费 |
| 3 | **版本节奏**：里程碑几个、`y` 位绑里程碑还是绑发布批次 | 决定 ROADMAP 的结构，事后改成本极高 |
| 4 | **覆盖率目标**：里程碑/集成/关键模块三档各多少 | 决定测试套件的分层粒度 |

若用户只说了「想搭个骨架」，用下面的默认值提议，但**必须让他确认**：

```
能力边界：由他填（不可代填）
规模：单进程 + 单库；不做分布式、不做计费
版本节奏：y 位绑里程碑（M01 → 0.1.z）
覆盖率：里程碑 80% / 全局集成 75% / 核心纯函数 100%
```

## 二、生成骨架

### 2.1 目录结构

```
<project>/
├── README.md          # 定位、从哪读起、设计要点速览
├── AGENTS.md          # 开发规约（强制）
├── ROADMAP.md         # 里程碑 × 版本号（唯一权威）
├── CHANGELOG.md       # 变更记录（只记用户可感知的变化）
├── .gitignore
├── docs/
│   ├── architecture/  # 架构与规格（NN-slug）
│   ├── research/      # 调研（NN-slug，顺延编号）
│   ├── milestones/    # 里程碑（Mxx-slug）
│   └── decisions/     # 决策记录（D<N>-slug）
└── _refs/             # 外部参考源码快照（gitignore，不入库）
```

**四个 docs 子目录一个都不能少**——它们对应四类产出，混放会让后期检索失效。

### 2.2 五个顶层文件的职责边界

| 文件 | 只写什么 | **不写**什么 |
|---|---|---|
| `README.md` | 定位、三条设计公理、目录导航、从哪读起 | 不写实现细节、不写里程碑清单 |
| `AGENTS.md` | 强制规约：栈约束、版本规则、门禁、文档规范、**明确不做的事** | 不写进度、不写计划 |
| `ROADMAP.md` | 里程碑 ↔ 版本号映射（**唯一权威**）、决策索引、入口/阶段路线 | 不写设计理由、不写任务细节 |
| `CHANGELOG.md` | 用户可感知的变化 | 不记重构、格式化、注释、测试补充 |
| `docs/*` | 各自领域的长文 | 不重复顶层文件已有的内容 |

> **判据**：同一句话如果只能放在一个地方，放哪？——放「最容易被查阅」的那个，其余地方用双链指过去。

### 2.3 版本号绑定（最容易做错的一条）

采用 `x.y.z`：

```
x — 主版本：只在「对已有用户数据/接口不兼容」时递增。x=1 表示首个可对外交付版。
y — 里程碑：与里程碑编号强绑定。M01 → 0.1.z，M02 → 0.2.z。
z — 里程碑内小迭代：每次增量交付递增。
```

三条铁律：

1. **里程碑验收通过时打 `.0`**（M04 通过 → `v0.4.0`）
2. **里程碑内补充用 `.1`、`.2`……**，**不得**用下一个 `y` 表示
3. **跨越里程碑时**必须同步更新 ROADMAP 与 CHANGELOG

## 三、写「明确不做的事」

这是 `AGENTS.md` 里**最不能省**的一节。格式：

```markdown
## 明确不做的事

| 不做 | 原因 |
|---|---|
| 多 agent 团队 | 收敛原则；先做好单 agent |
| 通用 workflow 编排 | 不需要；会引入平台化负担 |
```

写法要求：

- **每条必须带原因**，否则下一个人会重新提议它
- 原因写「为什么不划算」，不写「暂时不做」——后者等于没拒绝
- 项目成熟后可以移除条目，但**不要在没有决策记录的情况下悄悄删掉**

---

## 四、验收门禁（写进 AGENTS.md）

每个项目都应有一份**可勾选的**门禁清单，至少包含：

```
[ ] 本阶段测试覆盖率达标（按项目设定的阈值）
[ ] 无新增未记录的技术债
[ ] ROADMAP 与 CHANGELOG 已同步
[ ] 版本号已按规则更新
[ ] 用户已确认
```

门禁的价值不在于「有没有写」，而在于**每一项都能被判真伪**。写「质量达标」是废话，写「覆盖率 ≥80%」才是门禁。

## 五、反模式（实际踩过的坑）

| 反模式 | 后果 | 正确做法 |
|---|---|---|
| 先写代码后补规约 | 规约永远补不上，或补成事后合理化 | 骨架先行，一个文件不写代码也能建 |
| 里程碑按「功能模块」切 | 每个里程碑都无法独立验收 | 按「用户可感知的能力」切，每个里程碑能独立跑通 |
| AGENTS 写成愿望清单 | 没有约束力 | 只写可验证的规则；愿望写进 ROADMAP 或直接删 |
| 目录里塞 `misc/`、`notes/`、`tmp/` | 半年后无人知道哪个是权威 | 四类产出四个目录，其余不建 |
| 版本号随手涨 | 版本号失去信息量 | `y` 位绑里程碑，`z` 位绑迭代，写进 AGENTS |
| 不做 `.gitignore` 就 `git add .` | 几 GB 参考源码进库 | 先建 `.gitignore`，把参考快照目录排除 |

## 六、输出与自检

交付后必须做一次自检：

```
[ ] 五个顶层文件齐备，且职责无重叠
[ ] docs 四个子目录齐备（可空）
[ ] .gitignore 已排除参考快照与大文件
[ ] AGENTS 含「明确不做的事」且每条带原因
[ ] AGENTS 含可勾选的验收门禁
[ ] 版本号规则含「y 位绑里程碑」与三条铁律
[ ] ROADMAP 声明自己是「版本号唯一权威」
[ ] README 给出「从哪读起」的导航表
```

若有任何一项没做到，**不要交付**——骨架错了，后面所有文档都会歪。
