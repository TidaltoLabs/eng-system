# eng-research · 调研协议

调研的目的不是「收集资料」，而是**让下一个决策有据可依**。

> 模板：`../../templates/research.md.tpl`。若宿主提供插件根路径变量，优先使用。

---

## 一、来源标注（强制）

每一句结论都必须能归入以下四档之一：

| 标注 | 含义 | 要求 |
|---|---|---|
| `[官方]` | 官方文档/源码原文可支持 | **必须给链接 + 引用原文** |
| `[推断]` | 基于原文结构的工程判断 | 必须说明推理链 |
| `[待确认]` | 官方未覆盖，需实测 | 必须写「何时验证、怎么验证」 |
| `[未找到]` | 查过但无此内容 | 说明查了哪些来源（≠「不存在」） |

### 为什么要四档而不是「可信/不可信」

- `[推断]` 不是缺点——大量工程结论只能靠推断。问题在于**不标注**，让读者误以为是官方承诺。
- `[未找到]` 不等于「不存在」。写上它，是为了让下一个人知道「这里确实花过时间」，而不是重复劳动。

## 二、质量标准

**合格调研的唯一标准：结论能直接支撑一个具体决策。**

| 合格 | 不合格 |
|---|---|
| 「X 不支持 A，因此我们只能走 B；代价是 C」 | 「X 功能丰富，生态活跃」 |
| 「官方原文写『5 秒内必须响应』，所以同步调 LLM 必然超时」 | 「需要注意响应时间」 |
| 「三份存档 + 线上页共六处一致，判定可信度中高」 | 「据网上说……」 |

### 三条硬要求

1. **给证据，不给印象**：引用原文、给 `file:line`、给 Wayback 链接，而不是转述二手说法
2. **区分「历史结论」与「当前现状」**：带发布日期的文档才有时间意义
3. **必须有「对前序的修订」一节**：如果本次推翻了之前的判断，明写推翻了什么、为什么

## 三、五类常见谬误（反模式，都实际踩过）

### ① 把「没人做」当成「不该做」

> 发现社区没有实现某能力，于是判定「不该做」。

**这是方法论错误。** 「没人实现」是市场信号，不是价值判断。差异化恰恰长在别人不做的地方。

正确读法：**先问「为什么没人做」**——是技术不可行？成本过高？还是**需求真实存在但没人满足**？只有前两者才构成"不该做"的理由。

### ② 把过期文档当现状

上游项目改名、协议变更、能力下线后，旧文档不会自动消失。

**做法**：重要结论必须核实「页面更新时间」；有冲突时用 Wayback 存档做差分，判断哪个是当前口径。若官方没发公告只是静默改文档，**必须明说「无官方公告」**，不要把文档现状包装成官方承诺。

### ③ 把推断写成结论

「看起来支持」「应该可以」混进结论区，下游按官方承诺去设计，最后发现是推断。

**做法**：结论区只放已验证的事实；推断单独成节，并标注推理依据。

### ④ 资料汇编冒充调研

把官网首页、README、三篇博客拼起来，没有取舍、没有结论、没有代价分析。

**判据**：如果读完不知道该选哪个方案，就不是调研，是文献综述。

### ⑤ 忽略「平台外的约束」

只核实了「API 能不能调」，没核实「要什么资质、要多少钱、要不要上架、会不会违规」。

**做法**：每个候选至少核实四维——**能力 / 门槛 / 成本 / 合规**。

## 四、报告结构

```markdown
---
title: <阶段> · <主题>
type: research-report
status: completed
updated: YYYY-MM-DD
related: ["[[相关文档]]"]
---

# NN · <主题>

> 方法：<用了什么手段取证；数据快照日期>

## 零、结论（先给答案）

1. …（每条一句，可直接引用）
2. …

## 一、<主体一>

## 二、<主体二>

…

## 末、对前序的修订

| 原表述 | 修订 |
|---|---|

## 待确认

| # | 事项 | 影响 | 何时验证 |
```

**要求**：结论放最前，证据放中间，修订与待确认放最后。读者应该在 30 秒内知道答案，再决定要不要读细节。

## 五、多轮调研的编号与留痕

- 编号顺延：`docs/research/01-…`、`02-…`，**不得复用已占用编号**
- 每轮独立成文，**不修改历史报告的论证部分**——推翻结论时写进新报告的「对前序的修订」表
- 索引文件（`docs/research/README.md`）是**调研索引的唯一权威**，五列：编号 / 文档 / 阶段 / 状态 / 一句话结论

> **为什么保留错误的历史报告**：可追溯性。半年后有人问「当初为什么这么定」，需要看到当时的证据与推理，而不是只有最终结论。

### 事实性错误 vs 结论性推翻（两种处理，不要混）

| 情况 | 处理 | 例 |
|---|---|---|
| **事实性错误**（数字错、字段名错、链接失效） | **就地改**，并在修订表记一行 | `40184001` → `40054004` |
| **结论性推翻**（判断反了、方案被否） | **不改旧正文**，在新报告的修订表里写明 | 「微信不能主动推送」→「能，走某通道」 |

判据：改完之后，旧的推理链是否还成立。成立就就地改；不成立就留痕。

## 六、推翻之后要改哪些文件（fan-out 清单）

一条结论被推翻，受影响的不止调研本身。**按顺序过一遍，漏一步就会留下阻断级矛盾**：

```
① 新调研的「对前序的修订」表        ← 记录推翻
② 历史调研正文                      ← 只改事实性错误，结论性不动
③ 架构文档                          ← 追加「校准」节，status 升 draft-vN
④ 决策记录                          ← 草稿期原地改；已冻结则标 superseded
⑤ ROADMAP 的决策索引 / 阶段摘要      ← 旧条目标 🔁 并注明被谁取代
⑥ 受影响里程碑的非目标 / 交付物 / 门禁
⑦ CHANGELOG                         ← 记一条「变更」
⑧ 各索引的一句话结论                 ← 摘要必须与正文一致
```

**判据**：改完后，全库搜索旧结论的关键词，应该只在「修订记录」里出现。

## 七、派生子任务时怎么写任务书

当把取证工作分派给多个执行者时：

| 必须写清 | 为什么 |
|---|---|
| **要核实的具体断言**（越具体越好） | 否则会得到一篇泛泛的综述 |
| **要求给出 `file:line` 或链接** | 否则无法复核 |
| **要求标注四档来源** | 否则推断会被当成结论 |
| **要求「查不到就说查不到」** | 否则会被编造填补 |
| **说明哪些结论会决定什么** | 让执行者知道优先级 |

**明确禁止项也要写进去**，例如：「禁止编造清单字段名和目录路径」「不要把营销文案当现状」。

## 八、自检清单

```
[ ] 结论区每条都能直接支撑一个决策
[ ] 每个 `[官方]` 都有链接与原文引用
[ ] 每个 `[待确认]` 都写了「何时、如何验证」
[ ] 有「对前序的修订」一节（若本次推翻过任何结论）
[ ] 核实了页面/文档的更新时间
[ ] 每个候选都覆盖了「能力 / 门槛 / 成本 / 合规」四维
[ ] 没有把「没人做」写成「不该做」
[ ] 新增编号未与既有编号冲突
```
